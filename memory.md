# WatchDog project memory

Updated November 18, 2026. WatchDog is a single-owner macOS distraction blocker. Keep observation and browser Automation in the login-session GUI. The root daemon owns machine-wide enforcement, active block timers, and the cooling-off period. An administrator can recover the machine using `docs/RESCUE.md`.

## Build and installation

- `project.yml` is the XcodeGen source. Regenerate the ignored Xcode project with `xcodegen generate`. The app and daemon share `Packages/WatchDogCore`. Debug uses the `.dev` identity. Release uses `local.watchdog` and enables armed enforcement.
- **Self-build:** the builder's team (and optionally signing identity) goes in `Config/Local.xcconfig`, ignored by git and copied from `Config/Local.example.xcconfig`. `Config/Signing.xcconfig` includes it, and `install-armed.sh` reads it after `Signing.xcconfig`, so its values win in both. Run `scripts/build-armed.sh`, then `sudo scripts/install-armed.sh`. The app and daemon derive their XPC peer requirements from their own signing team. A process without a signing team denies its peer.
- **Public release:** the publisher team is pinned separately in `Config/Distribution.xcconfig` and must be committed (downloads are verified against it). It is empty while there is no Developer ID, and both scripts refuse `--distribute` / `--download` until it is set. On the signing Mac, use the publisher's Developer ID Application certificate and private key. Configure the notary profile once with `xcrun notarytool store-credentials WatchDog-Notary`. Run `scripts/build-armed.sh --distribute`; `NOTARY_PROFILE` selects another stored profile. The script publishes `build-armed/WatchDog.zip` after Apple accepts the submission, the ticket is stapled, and the extracted download passes verification.
- **Install a download:** expand the ZIP as the ordinary user. From a trusted checkout, run `sudo scripts/install-armed.sh --download "/absolute/path/to/WatchDog.app"`. The installer stages the bundle under root's home, normalizes ownership and permissions, verifies both signing identifiers and the publisher's Developer ID, and requests a Gatekeeper assessment. A self-build uses its independently configured signer. Installation uses an exclusive rename and refuses to replace an existing app or running armed daemon. The current bundle layout contains regular files and directories only.
- Hardened Runtime is enabled on both Release targets. The GUI alone receives `com.apple.security.automation.apple-events`. macOS manages the browser Automation and Accessibility prompts. Build or signature verification failures stop the release workflow.

## Owner and session security

The privileged XPC listener checks the client's code signature and effective UID before exposing status or controls. The armed installer records the invoking sudo user's UID. For a direct-root install, development build, or migration, use **Setup → Enroll This Account…** with the updated service registered. Enrollment requires administrator authorization and the foreground console session. Heartbeats must match both the owner UID and the active audit session. Switching users clears previous health information. Existing timed blocks remain machine-wide.

## Optional packet filter

Hosts enforcement runs before PF and continues when PF stands down. Installation requires a stock on-disk configuration and a complete live match for the filter, NAT, dummynet, tables and top-level anchors. Updates also verify WatchDog’s private anchor. Root changes use filter-only input. Teardown always empties WatchDog’s own anchor first, whatever else PF holds, so a block never outlives its end; it restores the stock root filter only when the live state is exactly stock plus WatchDog’s reference, and otherwise leaves the root alone (the reference to an empty anchor matches nothing, and the next block may install from that state). Teardown fails, keeping the recovery receipt and retrying, only when WatchDog’s anchor cannot be confirmed empty. A failed token release is logged and expires at restart. The rescue script and RESCUE.md empty the anchor with `pfctl -a <id> -F rules` and `-F Tables`, never the main ruleset, and do not release a saved token (it may be from an earlier boot).

The daemon compiled, the core suite passed, and a simulated PF command runner exercised installation, DNS updates, teardown and crash recovery without changing the live firewall. The generated filter syntax passed the macOS PF parser. A privileged install/block/unblock cycle still needs verification on a test Mac. Inspection and filter replacement are separate kernel operations, so another privileged PF writer can change rules between them.

## Addressed after the security review (2026-11-18, not yet run live)

- **Daemon state privacy:** the daemon runs with umask 077 and on start makes its state folder root:wheel 0700 and every regular file in it 0600, which tightens existing installs. Files other programs read set their own modes (hosts 0644, browser policy 0644, `/Library/Managed Preferences` 0755, owner record 0644). Reading the audit log or `hosts.backup` now needs sudo; Settings and RESCUE.md say so.
- **Agent health:** each heartbeat carries `secondsSinceEvaluation` (awake time since the last successful rule check, stamped by the background sender) and `waitingOnBrowser` (an Apple Event call is in progress, see `AppleEventWait`). `AgentHealth.isHealthy` requires `canSee` and a check within `Limits.evaluationGraceSeconds` (90 s), or `browserPromptGraceSeconds` (300 s) while waiting on a browser. A stalled app now triggers the penalty block even while heartbeats arrive; the audit log says "the app stopped checking the rules".
- **Recovery ownership:** the browser-policy marker now holds a copy of the policy WatchDog wrote. The daemon and `uninstall.sh` treat a policy as WatchDog's only if it matches that copy or is exactly `{"TorDisabled":true}` (covers older empty markers); anything else is kept. `uninstall.sh` and the RESCUE.md hand steps strip hosts like the daemon: inside the section only `0.0.0.0` / `::` lines go, and a missing end marker cannot swallow the rest of the file. The hand steps show a `diff` before writing.

## Pomodoro timer (2026-11-18, built, not yet run live)

Settings → Pomodoro picks the timer: built-in (`PomodoroMachine` in WatchDogCore, driven by `App/PomodoroTimer.swift`) or Session (read-only, unchanged). Both feed `timer_state`; PLAN.md §19 has the semantics. The built-in timer keeps time on the trusted counter, keeps its state in the user-owned `timer.json`, and stores sessions and categories in the usage database (migration `4-sessions`). It does not touch the daemon or enforcement; "Pomodoro it" remains the rule that cannot be argued with. The core suite now has 123 tests. The Focus pane, popover controls, Settings section and notifications have not been seen on screen.

## Usage history privacy (2026-11-18, built, not yet run live)

- Settings → History → "Page addresses" (`AddressDetail`, key `history.addresses`): **Site only** (default: `https://www.youtube.com`, no path, query or fragment), **Full, sensitive parts removed** (`LinkScrubber`), or **Full**. Rules match sites and titles either way; the host is never changed.
- `LinkScrubber` is best effort, by pattern: drops `user:password@`; blanks values of parameters named like secrets or identities (token, key, password, session, signature, code, email, phone, user, also `;jsessionid=` in the path and `#access_token=` in the fragment); and anywhere replaces email addresses, JWTs, Luhn-valid card numbers, hex of 32+ characters and 24+ character runs with 2+ digits that keep switching case (generated keys) with `redacted`. Links inside links (`?next=https://...`) are cleaned too. Known gaps: generated keys with fewer than two digits, secrets under innocent parameter names, search terms (kept on purpose). Window titles are not scrubbed.
- The expiry job (a minute after launch, then every 6 hours) also brings stored addresses down to the current setting (`UsageStore.applyAddressDetail`), so the first launch of this build reduces existing full addresses to sites. It runs on the timer rather than on the settings change so a mis-click put back soon after costs nothing.
- Retention (`HistoryRetention`, `UsageStore.prune`): window titles, addresses and track names are cleared after 30 days, activity (spans, sound, rule firings) is deleted after a year; both settable, with floors of 7 and 30 days because rules look back at most 24 hours. Pomodoro sessions are kept. The app prunes a minute after launch and every 6 hours. The owner approved these as defaults on 2026-11-18, changeable in Settings; the oldest data on this Mac is from 2026-11-17, so nothing would be cleared before mid-December.
- `usage.sqlite` is now 0600 in a 0700 folder (it was 0644/0755, protected only by `~/Library` being 0700), and SQLite `secure_delete` is on so cleared rows are overwritten.
- A span can no longer run backwards: if the clock steps back (the app switching to the daemon's clock after starting with a moved system clock), `UsageStore.record` starts a new span instead of moving the end before the start. A backwards span would have subtracted from rule totals and given "Pomodoro it" break budget back. The rule engine also counts any older backwards span as zero.
- The per-build prompt is macOS's "access data from other apps" (`kTCCServiceSystemPolicyAppData`, confirmed in the tccd log at the 01:04 launch), raised by reading Session's group container. With the built-in timer selected WatchDog no longer reads that file.

## Third security review (2026-11-18, independent read of daemon, XPC, installer; fixes built, not run live)

Fixed and unit-tested (core suite 133 tests):
- Proposals with two rules under one ID are refused (`ConfigPolicy.decide`); a quiet twin could otherwise keep an enforcing rule silent through their shared cooldown.
- Refused domain text is escaped (`Limits.printable`) and every audit line is escaped as a backstop, so a string with a line break cannot forge audit entries.
- Firewall addresses are validated on their bytes: IPv6 multicast (`ff02::…`, needed by neighbour discovery), IPv4-mapped/compatible forms, documentation, shared (100.64/10) and benchmarking (198.18/15) ranges are refused; NAT64 addresses are judged by the IPv4 address inside. These come from DNS answers that a blocked site's owner controls.
- Killing open connections for a new IPv6 address uses `::/0` (the IPv4 wildcard matched nothing).
- RESCUE.md uses `mktemp` instead of a fixed `/tmp/hosts.clean` another account could prepare.
- `uninstall.sh`: fixed `PATH`; stops with an error if the daemon is still loaded after `bootout` (it would put the hosts section back); quits only this build's app by bundle ID (launchd starts the app as plain `Contents/MacOS/WatchDog`, so the old `pkill -f` pattern never matched it).
- `spike-brave.sh revert`: a lost end marker no longer deletes the rest of `/etc/hosts`; the Brave policy is removed only if it is still the test policy.

## Open findings

| Area | Finding and next action |
|---|---|
| Daemon trusts any team-signed build (medium) | The XPC requirement is identifier + team + owner UID. The owner can rebuild Release with the dev commands, `kill -STOP` the app (launchd only restarts exited jobs) and send healthy heartbeats from Terminal, with no password and nothing in the audit log; malware with access to the signing key could too. A nil `secondsSinceEvaluation` also counts as healthy. Fix: pin the installed app's cdhash (or path via audit token) at install; reject nil in the armed build; have `install-armed.sh` re-check runtime flags and `get-task-allow` on local builds. |
| Brave policy shared by both builds (medium) | Same path for dev and armed, and a policy equal to `{"TorDisabled":true}` counts as ours. The dev daemon (dry run, restarts every 15 min) or plain `sudo uninstall.sh` deletes the armed build's policy, and the armed daemon caches `applied` and never re-checks. No impact until the armed build is installed. Fix: dev never writes the real policy (or tags its content); drop the content fallback when another build's marker exists; re-check the file each tick like hosts. |
| Firewall and never-block list (medium) | Address blocking can still hit never-block sites or the DNS resolver when they share addresses with a blocked site. Fix in the daemon: resolve `Limits.neverBlock` and subtract, and exclude the current resolvers (`scutil --dns`). |
| Enrollment admin check (plausible, live test) | The daemon (root) asks for `system.privilege.admin` without interaction; that right has `allow-root`, so the check may pass for any client. The listener needs a team-signed client, but a Debug build has no hardened runtime (code can be injected). Risk only while no owner record exists. Test it; fix with a custom right that has `allow-root` false, or check who authenticated. |
| `/Applications` is root:admin 775 (plausible, live test) | An admin-group process may rename the root-owned bundle without a password. Test whether the registered daemon then runs a replacement team-signed binary. If so, install the daemon as a classic `/Library/LaunchDaemons` job pointing at a root-only path. |
| Hosts writer (low) | Another root tool's edit between the daemon's read and rename is lost; a symlinked `/etc/hosts` becomes a regular file. Compare inode/mtime/size before the rename; write through a symlink's target. |
| Firewall crash recovery (low) | The receipt's age is compared with `kern.boottime`, which moves with the clock. Store `kern.bootsessionuuid` (`TrustedClock.bootSessionID()`) instead. |

Checked and found sound in that review: every root write uses a fixed path in a root-only folder, nothing from XPC reaches a path, the owner record is read with `O_NOFOLLOW`/`fstat` and published with `mkstemp` + `link`; domain syntax, hosts section handling, PF input and AppleScript inputs leave no injection route; subprocesses use absolute paths and argument arrays; the installer's staging, link rejection, exclusive rename and rollback hold.
